# Community Hub 2.3.15 — Two-Hub discovery and sync test

## 1. Separate public endpoints

For two Hubs behind the same public IP, use different public ports and separate data volumes:

- Hub A: `http://PUBLIC_IP:8182`
- Hub B: `http://PUBLIC_IP:8181`

Each Hub must advertise its own URL (`HUB_PUBLIC_URL`) and its own mapped port (`HOST_PORT` / `P2P_PUBLIC_PORT`). Do not set both Hubs' `HUB_PUBLIC_URL` to the same endpoint. Forward TCP 8181 and 8182 to the matching SoloHost services.

## 2. Discovery

1. Add/verify one trusted Hub using its public URL.
2. Wait for a signed Federation handshake (`Healthy` / verified identity).
3. The verified Hub now returns a bounded rendezvous list containing itself and trusted/bootstrap peers with verified public endpoints.
4. The receiving Hub stores returned Hubs as `discovered` contacts and schedules signed handshakes for them.
5. Connected libp2p peers are eligible bridge crawlers; they are no longer skipped by `PeerCrawler`.

A verified HTTP/Federation handshake is not the same as a live libp2p WebSocket connection. The Network page shows these states separately and exposes the latest dial error.

## 3. Public post synchronization

Content replication is intentionally opt-in:

1. On Hub A, open Network → Network settings → enable public post synchronization.
2. Do the same on Hub B.
3. For the intended trusted peer, leave its per-Hub “Sync public posts” switch enabled. The global switch enables trusted/bootstrap peers on that Hub; the per-peer switch can turn an individual link off.
4. Create a public post on A and wait for the next sync cycle or press “Sync now” on B.
5. Confirm the public post appears on B and the received-event counter advances.

Both sides must permit content sync. Private/local events and private messages are not replicated. Discovery metadata can still be exchanged while content sync is off.

## 4. If P2P still reports 0 links

Check the technical details / P2P dial error. Confirm the advertised multiaddr uses the correct public IP and port, that the matching TCP port is forwarded, and that the SoloHost reverse proxy preserves WebSocket Upgrade requests. If both Hubs are tested from the same LAN, NAT loopback support may affect testing; verify from an external network too.
